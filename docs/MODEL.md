# Где модель и как она работает

Обученная модель — не LLM и не набор текстовых рекомендаций. Это логистическая регрессия: шесть числовых признаков преобразуются в вероятность реализации риска до завершения проекта. Предиктор используется для каждого риска реестра. Из этих вероятностей система рассчитывает ожидаемые потери, приоритеты и оптимальный портфель мер.

[Карта всех слоёв проекта](ARCHITECTURE.md).

## Исходники

| Файл Kotlin | Ответственность |

| `model/response/ml/ModelVersion.kt` | Экспортируемый артефакт без исходных строк истории |

Все пути относительно `src/main/kotlin/com/evedenta/riskpilot/`. Один файл содержит один класс, объект или enum с совпадающим именем.

## Параметры обученной модели

[model-artifact.json](model-artifact.json) — экспорт модели стандартной демонстрации. Актуальная активная модель выгружается через `GET /api/model/artifact` и кнопку в ML-лаборатории. JSON содержит идентификатор версии, дату обучения, источник, коэффициенты, интерсепт, средние и масштабы признаков, порог и метрики. Для инференса исходная история не нужна. БД дополнительно сохраняет CSV, чтобы версию можно было изучить и обучить заново.

Порядок признаков: сложность, опыт команды, загрузка, зависимости / 10, изменчивость требований, надёжность поставщика. После стандартизации модель суммирует произведения признаков на коэффициенты с интерсептом и применяет sigmoid. Вклады в log-odds показаны в интерфейсе; они не доказывают причинность.

## Обучение в интерфейсе

1. Откройте **ML лаборатория**. Вверху видны версия, дата, источник и размер истории.
2. Скачайте образец CSV. Заголовок фиксирован: `project_id,complexity,experience,workload,dependencies,volatility,reliability,occurred`.
3. Загрузите CSV с известными историческими исходами и нажмите **Поставить в очередь**; для явного немедленного обучения есть **Обучить сейчас**. Минимум 90 записей и 30 проектов, максимум 5000 записей / 1 МБ. `occurred` — 0 или 1. Шесть признаков должны описывать состояние до события.
4. Целые проекты разделяются 70/15/15. Нормализация и обучение используют train, порог подбирается по validation, качество оценивается на test. В каждой части должны быть оба класса. Некорректная загрузка не заменяет активную версию.
5. При обучении новая версия и её история сохраняются в БД. Все риски пересчитываются. После перезапуска активная версия восстанавливается без нового обучения.
6. Сравните ROC AUC, Brier и калибровку. Если качество хуже, активируйте прежнюю версию в таблице.
7. Используйте форму единичного прогноза, чтобы проверить конкретные значения признаков без изменения реестра.

Кнопка **Учебная модель** создаёт новую воспроизводимую версию на синтетических данных. Факт пользовательской загрузки не подтверждает достоверность данных. Переключение версий сравнивает их на собственных тестовых частях; для строгого сравнительного эксперимента необходим единый внешний holdout. Модель используется как часть экспертного решения, а не автоматическая гарантия вероятности.

## Как обучается модель

1. История содержит шесть признаков, идентификатор проекта и известный исход `occurred` (0/1).
2. `ProjectDatasetSplitter` отделяет целые проекты: 70% train, 15% validation, 15% test, seed 42. Средние и масштабы вычисляются только на train.
3. `LogisticRegressionTrainer` вызывает `Smile LogisticRegression.binomial`: L-BFGS минимизирует логистическую ошибку с L2. Лимит 500 итераций, tolerance 1e-6, регуляризация 0,01 для средней ошибки (в Smile передаётся 0,01 × размер train). Обучаются шесть весов и интерсепт.
4. На validation подбирается порог 0,20–0,80 по balanced accuracy. На test вычисляются итоговые метрики. Параметры экспортируются в JSON; `LogisticRegressionModel` применяет их без повторного обучения.

Используется Smile 4.4.2, совместимая с JDK 21. Реализация оптимизатора — библиотечная; разделение проектов, нормализация, контроль качества и жизненный цикл остаются кодом приложения. [Исходник Smile](https://github.com/haifengl/smile/blob/v4.4.2/core/src/main/java/smile/classification/LogisticRegression.java), [Spring Scheduler](https://docs.spring.io/spring-framework/reference/integration/scheduling.html).

## Планировщик

`ModelRetrainingScheduler` вызывает `ModelRetrainingService` ежедневно в 03:00 по Москве. Cron Spring содержит шесть полей: `0 0 3 * * *`. Сервис сохраняет очередь и журнал в PostgreSQL. Приоритет источников: существующий `training-data/history.csv` → последний загруженный CSV в БД → история активной модели. Docker монтирует папку только для чтения. Обновляйте файл атомарной заменой; некорректный файл приводит к FAILED без переключения модели.

Отпечаток SHA-256 включает нормализованный CSV, версию алгоритма и параметры. Уже проверенный набор пропускается. При отсутствии новых данных модель сама по себе лучше не становится. Новые исходы проектов нужно собирать и добавлять в историю.

Автоматическое переключение допускается, если на validation AUC ≥ 0,55, Brier не хуже константного прогноза и не хуже текущей модели более чем на 0,005. Обе модели сравниваются на одной validation-части нового набора. Test не участвует в выборе версии. Отклонённый кандидат сохраняется для просмотра, активная версия остаётся прежней. Это внутренний фильтр качества, а не доказательство переноса на реальные проекты. При многократных экспериментах нужен отдельный внешний holdout.

**Проверить сейчас** запускает тот же процесс с фильтром качества. **Обучить сейчас** и ручная активация версии — явное решение пользователя и могут обойти автоматический фильтр. Журнал содержит время, источник, статус ACTIVATED / REJECTED / SKIPPED / FAILED и причину. Первый запуск создаёт синтетическую учебную модель; существующая версия после рестарта загружается из БД. Старые артефакты ручного градиентного алгоритма поддерживаются и помечаются legacy.

| Переменная .env | По умолчанию |
|---|---|
| ML_RETRAIN_ENABLED | true |
| ML_RETRAIN_CRON | 0 0 3 * * * |
| ML_RETRAIN_ZONE | Europe/Moscow |
| ML_TRAINING_CSV | ./training-data/history.csv |
| ML_MIN_VALIDATION_AUC | 0.55 |
| ML_MAX_BRIER_REGRESSION | 0.005 |

После изменения `.env` выполните `docker compose up -d`. Приложение должно работать в назначенное время; пропущенные запуски не догоняются. Блокировка параллельных запусков действует внутри одного экземпляра приложения: MVP рассчитан на один экземпляр, для нескольких нужен распределённый lock.
