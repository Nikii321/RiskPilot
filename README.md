# RiskPilot

СППР управления проектными рисками. Kotlin + Spring Boot, PostgreSQL, аналитическая панель и Docker Compose.

**[Карта пакетов и точек входа](docs/ARCHITECTURE.md)** · **[Что уже можно делать в системе](docs/FEATURES.md)** · **[Где ML-модель и как её обучать](docs/MODEL.md)**. Есть загрузка CSV, обучение и версии ML, собственные меры снижения риска, история и сравнение решений. Прототип объединяет все восемь практик: постановку, AHP, неопределённость, оптимизацию, базу знаний, прогноз, рекомендации и интеграцию.

## Быстрый запуск

Нужны работающий Docker Desktop / Docker Engine и Docker Compose v2.

```sh
cp .env.example .env
docker compose up --build -d
```

Откройте [http://localhost:8080](http://localhost:8080). Первая сборка загружает Gradle, JDK-образ и зависимости и запускает тесты. Восемь демонстрационных рисков создаются один раз. Данные хранятся в PostgreSQL volume `postgres_data` и переживают перезапуск.

```sh
docker compose ps
docker compose logs -f app
docker compose down                  # остановить, сохранив БД
```

`APP_PORT` в `.env` меняет внешний порт. `DB_PASSWORD` задаёт пароль БД; при изменении пароля существующего volume сначала измените пароль пользователя PostgreSQL. Команда `docker compose down -v` **удаляет данные** и нужна только для намеренного полного сброса демонстрации.

Приложение доступно только на localhost. БД наружу не опубликована. MVP однопользовательский, без аутентификации; перед публичным размещением необходимы контроль доступа и аудит.

## Локальная разработка и IntelliJ IDEA

Сохранены исходные Gradle Wrapper, Kotlin 2.3.21, Spring Boot 4.1.2 и пакет `com.evedenta.riskpilot`. Откройте `build.gradle.kts` как Gradle-проект, выберите JDK 21 в Project SDK и Gradle JVM и выполните Sync. Запускайте `RiskPilotApplicationKt` или:

```sh
./gradlew test
./gradlew bootRun
# либо
./gradlew bootJar
java -jar build/libs/RiskPilot-1.0.0.jar
```

Без переменных окружения используется файловая H2 в `./data`. PostgreSQL включается через `DB_URL`, `DB_USER`, `DB_PASSWORD`. Само приложение и Docker используют одни и те же JDBC-запросы. Не запускайте два экземпляра локального приложения с одним файлом H2.

## Как продемонстрировать систему

1. Откройте обзор: восемь рисков, карта вероятности и ущерба, категории и итоговый план.
2. В ML-лаборатории загрузите CSV для явного обучения, скачайте артефакт JSON и проверьте единичный прогноз. При необходимости переключитесь обратно на учебную версию.
3. В реестре откройте риск и измените признаки. Прогноз вероятности и все связанные расчёты обновятся после сохранения.
4. В AHP сравните четыре критерия. Верхний треугольник редактируется, нижний строится автоматически; CR > 0,10 блокирует принятие несогласованной модели.
5. В сценариях измените вероятности, сохранив сумму 1. Сравните принятие рисков, выбор по AHP и оптимальный портфель; рассмотрите VaR и CVaR.
6. В распределении ресурсов настройте свои меры: цена, трудозатраты, эффективность. Сохраните первый вариант кнопкой «Сохранить решение».
7. Уменьшите бюджет с 300 до 100 тыс. ₽ или трудовой ресурс с 25 до 6 чел.-дней. Посмотрите, какие меры останутся в портфеле. При нулевом бюджете платные меры не выбираются.
8. Сохраните второй вариант и сравните оба в истории решений.
9. В базе знаний проверьте факты и сработавшие правила; в ML — качество и вклад признаков конкретного риска.
10. В рекомендациях получите действие, стоимость, ожидаемый эффект и причину исключения альтернатив. «Экспорт решения» сохраняет JSON фактически рассчитанного состояния.
11. Перезапустите приложение и убедитесь, что изменения реестра сохранились.

## Обучение по расписанию

Обучение выполняет JVM-библиотека **Smile 4.4.2** (логистическая регрессия, L-BFGS, L2). Spring Scheduler ежедневно в **03:00 Europe/Moscow** проверяет историю. В ML-лаборатории можно поставить CSV в очередь, посмотреть следующий запуск и журнал, либо запустить проверку сейчас. Файл `training-data/history.csv`, если существует, имеет приоритет над очередью; затем используется история активной модели. Одинаковые данные и настройки повторно не обучаются. Кандидат активируется только после проверки validation AUC и Brier; предыдущая модель доступна для прогнозов всё время обучения.

Настройки в `.env`: `ML_RETRAIN_ENABLED`, `ML_RETRAIN_CRON`, `ML_RETRAIN_ZONE`, `ML_MIN_VALIDATION_AUC`, `ML_MAX_BRIER_REGRESSION`. После изменения пересоздайте приложение: `docker compose up -d`. Приложение должно работать во время запуска; пропущенные запуски автоматически не догоняются. Подробнее: [модель и расписание](docs/MODEL.md).

## Почему ML, а не LLM

Вероятность события по структурированным числовым данным оценивает логистическая регрессия с L2-регуляризацией. Она обучается на Kotlin без Python-сервиса и внешних API. Для рекомендаций используется проверяемый гибрид прогноза, AHP, оптимизации и продукционных правил. Формулировки воспроизводимы и основаны на числовом результате. Генеративная LLM не добавляет надёжности к этой постановке и для MVP не требуется.

**История синтетическая**: 300 проектов × 4 наблюдения = 1 200 записей, seed 42. Отложены целые проекты: 210 train / 45 validation / 45 test. Нормализация и обучение используют только train; порог выбирается по balanced accuracy validation; метрики считаются на test. При первом запуске создаётся учебная версия; далее активная обученная модель и её история восстанавливаются из БД. В ML-лаборатории можно обучить новую версию на CSV и вернуться к предыдущей. Качество на искусственных данных не доказывает качество на реальных проектах. История доступна через `/api/history.csv`; загрузить собственную историю можно в ML-лаборатории. Генератор учебной истории выделен в `SyntheticHistoryGenerator`, обучение — в `LogisticRegressionTrainer`, применение — в `LogisticRegressionModel`.

## Методы

- **AHP**: главный собственный вектор методом степенных итераций; CI, CR с RI = 0,90. Критерии: вероятность, прямой ущерб, задержка, срочность. Альтернативы сравниваются отношением значений; ноль заменяется на 10⁻⁶. Приоритет определяет внимание руководителя, денежный эффект — портфель.
- **Неопределённость**: три экспертных сценария с вероятностями 0,2 / 0,5 / 0,3. Множители вероятности 0,7 / 1 / 1,35; ущерба 0,8 / 1 / 1,3. Вероятность ограничена единицей. Сравнение Байеса, Вальда, Сэвиджа и Гурвица (вес лучшего исхода 0,6). Сожаление — относительно трёх показанных стратегий.
- **Монте-Карло**: 10 000 испытаний, seed 73, общий сценарий для всех рисков; события независимы условно на сценарий. Меры уменьшают тяжесть, а не вероятность. После мер в стоимость включены расходы на меры. VaR95 — эмпирический 95-й процентиль, CVaR95 — среднее верхних 5% (с граничным наблюдением).
- **Оптимизация**: множественный бинарный выбор; у каждого риска две меры и вариант без меры. Точный метод ветвей и границ максимизирует предотвращённые ожидаемые потери минус расходы. Ограничения: бюджет, человеко-дни, не более одной меры на риск. Верхняя оценка игнорирует ресурсные ограничения и потому безопасна для отсечения. MVP ограничен 14 рисками.
- **Стоимость**: все суммы в тыс. ₽. Полный ущерб = прямые потери + задержка × цена дня. Прямые потери должны исключать простой во избежание двойного счёта. Начальные шаблоны: базовая мера стоит floor(5,5% прямого ущерба), минимум 15; требует 3 дня и снижает ущерб на 35%. Расширенная вдвое дороже, 6 дней, снижение 60%. Цена, трудозатраты и эффективность редактируются для каждого риска; после сохранения используются собственные оценки.
- **База знаний**: шесть правил с прямым выводом и трассировкой фактов. Действия по безопасности и кадровым рискам видны даже при отсутствии финансирования.

## Структура

```text
src/main/kotlin/com/evedenta/riskpilot/
  controller/       # HTTP → сервисы; advice с обработкой ошибок
  service/          # сценарии анализа, рисков, мер, решений и ML
  repository/       # JDBC по функциям: risk, mitigation, decision, ml
  domain/           # понятия и предметные правила
  model/            # request, response и mapper
  ml/               # data, training, inference, model
  algorithm/        # ahp, optimization, scenario, knowledge
  config/           # настройки и начальные данные
  exception/        # предметные исключения
src/main/resources/static/   # автономная браузерная панель без CDN
src/test/                   # математические и HTTP интеграционные тесты
docs/                       # паспорт, API, результаты и инструкция к защите
Dockerfile                  # сборка с тестами, JRE 21, непривилегированный пользователь
compose.yaml                # приложение + PostgreSQL + проверки здоровья
```

[Описание API](docs/API.md). [Паспорт СППР](docs/Паспорт_СППР_RiskPilot.docx). [Результат расчёта](docs/demo-analysis.json).

## Проверка

`./gradlew test bootJar` запускает 23 проверки, включая архитектуру слоёв: AHP, жизненный цикл CSV/ML, экспорт и переключение моделей, собственные меры, сохранение/сравнение решений, независимое сравнение оптимизатора с полным перебором, ML, правила, проверку вероятностей сценариев, сопоставление имитации с аналитическим ожиданием и полный HTTP CRUD-цикл с конфликтом версий, отсутствующим риском и некорректным бюджетом. GitHub Actions настроен в корневой .github/workflows/ci.yml: при push и pull request запускаются тесты, сборка Docker Compose и smoke-запрос к API с PostgreSQL.
